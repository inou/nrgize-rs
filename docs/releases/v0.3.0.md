# v0.3.0

A failed deploy can now put the database back, and a rollback can too when you ask. Nothing breaks: scripts written for v0.2.0 run unchanged. The [changelog](https://github.com/inou/nrgize-rs/blob/main/CHANGELOG.md) has the full detail.

- Undo a migration when the deploy fails: the `deploy()` option `pre_deploy_undo` names a command that reverses `pre_deploy`. It runs once on the first host, from the new image, after the old containers are serving again, and also on Ctrl-C. It is skipped, with the command to run by hand, if any host could not be restored.
- Undo only what was applied: the option `pre_deploy_version` names a command that prints the schema version. `nrg` reads it before and after `pre_deploy`. If it did not change, nothing is undone; if it did, `{before}` in the undo command becomes the version from before.
- Undo on rollback, opt-in: `nrg rollback <service> --undo-pre-deploy` (stdlib `rollback(.., #{ undo_pre_deploy: true })`) also runs the undo saved with the rolled-back release. It refuses before touching a host when the undo would not be safe, for example when the database has moved since that release or only some hosts are rolled back.
- Builtin: `state_update(values, deleted)` writes and deletes state keys in one write.
- Docs: the site is rewritten around short guides with runnable examples and diagrams, and has its own look.

```rhai
deploy::deploy(global::HOSTS, "ghcr.io/acme/shop:" + tag, "shop", #{
    pre_deploy:         "bin/rails db:migrate",
    pre_deploy_version: "bin/rails db:version",
    pre_deploy_undo:    "bin/rails db:migrate VERSION={before}",
});
```

## Upgrading

No changes are needed. Releases deployed with v0.2.0 or earlier have no saved undo, so `--undo-pre-deploy` refuses for them; deploy once with v0.3.0 first. The [deploy guide](../deploy.md) covers the limits of the version check.
